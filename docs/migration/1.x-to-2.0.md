# Migrating from 1.x to 2.0

Version 2.0 splits the single `accessibility` package into a family of
eight, and the 2.0 UI packages are built on the standalone `material_ui`
and `cupertino_ui` packages that ship with Flutter 3.47.

Migrate if your app is already on `material_ui` or `cupertino_ui`. The
work is mechanical: new package names, an explicit repository load instead
of `AccessibilityInitializer`, and your own `MaterialApp` under a theme
builder instead of `AccessibleMaterialApp`.

Stay on branch
[`1.x`](https://github.com/RubenCesario/accessibility/tree/1.x) if your app
still uses the Material library of the Flutter SDK
(`package:flutter/material.dart`). `material_ui` is a copy of that code, so
its `ThemeData`, `Theme` and `ThemeMode` are different Dart types: the 2.0
packages cannot accept a legacy `ThemeData`. The `1.x` branch receives bug
fixes.

Your users keep their settings either way: the 2.0 storage adapter reads
the keys 1.x wrote. See [Stored settings](#stored-settings).

## Install

1.x was one dependency:

```yaml
dependencies:
  accessibility: ^1.4.0
```

2.0 is the packages the app actually needs:

```yaml
dependencies:
  # The design system layer: one of the two, or neither for a custom UI.
  accessibility_material: ^2.0.0
  accessibility_cupertino: ^2.0.0
  # Persistence. Without it nothing is stored.
  accessibility_shared_preferences: ^2.0.0
  # Optional: the Andika accessible font, ~2.5 MB.
  accessibility_font_andika: ^2.0.0
```

`accessibility_material` and `accessibility_cupertino` re-export
`flutter_accessibility` (which re-exports `accessibility`) and
`AccessibilityLocalizations`, so those four packages need no explicit
dependency. An app with its own settings UI and no design-system panel
depends on `flutter_accessibility` alone, plus a storage adapter.

The translations that 1.x pulled in unconditionally now come with the two
UI packages; `accessibility_localizations` is a direct dependency only for
an app that builds its own screen with the same strings.

## Start-up

### Material

Before (1.x):

```dart
final service = SharedPreferencesServiceWithCache(
  await createSharedPreferencesWithCache(),
);
final settings = await service.getLocalStorageAccessibilitySettings();
runApp(
  AccessibilityInitializer(
    sharedPreferencesService: service,
    accessibilitySettingsCollection: settings,
    child: MyApp(appThemes: AppThemes(lightTheme: ..., darkTheme: ...)),
  ),
);
// MyApp builds AccessibleMaterialApp(theme:, darkTheme:, home:)
```

After (2.0):

```dart
void main() async {
  WidgetsFlutterBinding.ensureInitialized();
  final repository = AccessibilitySettingsRepository(
    service: SharedPreferencesAccessibilityStorageService(),
  );
  await repository.load();
  runApp(
    AccessibilityScope(
      viewModel: AccessibilitySettingsViewModel(
        repository: repository,
        accessibleFonts: const [AndikaFont.font],
      ),
      child: const MyApp(),
    ),
  );
}

class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) => AccessibleThemeBuilder(
    theme: ThemeData(colorScheme: kLightColorScheme),
    darkTheme: ThemeData(colorScheme: kDarkColorScheme),
    builder: (context, themes) => MaterialApp(
      theme: themes.light,
      darkTheme: themes.dark,
      highContrastTheme: themes.highContrastLight,
      highContrastDarkTheme: themes.highContrastDark,
      themeMode: themes.mode,
      localizationsDelegates: const [
        ...GlobalMaterialLocalizations.delegates,
        AccessibilityLocalizations.delegate,
      ],
      supportedLocales: AccessibilityLocalizations.supportedLocales,
      home: const Scaffold(body: AccessibilitySettingsPanel()),
    ),
  );
}
```

What changed:

- `AccessibilityInitializer` is gone. Create the repository, `await`
  `load()` before `runApp`, and provide the ViewModel with
  `AccessibilityScope`. The load stays blocking on purpose: a
  non-blocking path shows a flash of unstyled content.
- `AppThemes` is gone. Pass your own `ThemeData` to
  `AccessibleThemeBuilder`; it yields an `AccessibleThemes` with `light`,
  `dark`, `highContrastLight`, `highContrastDark` and `mode`. Omitting
  `theme` / `darkTheme` uses `ThemeData.light()` / `ThemeData.dark()`.
- `AccessibleMaterialApp` is gone. Keep your own `MaterialApp` (or
  `MaterialApp.router`) inside the builder. `MaterialApp` picks the
  high-contrast themes itself when the OS asks for more contrast, which is
  why the builder produces four.
- The accessible font is opt-in: register it on the ViewModel with
  `accessibleFonts: const [AndikaFont.font]` from
  `accessibility_font_andika`. Leave the list empty and the font setting is
  not offered.
- The localizations delegate is added to the app's own list instead of
  replacing it.

An app that has its own high-contrast colour schemes applies the settings
to them itself instead of using the builder's two, with the transformation
behind the builder:

```dart
highContrastTheme: AccessibleThemeData.from(
  themeData: ThemeData(colorScheme: kHighContrastLightColorScheme),
  settings: AccessibilityScope.settingsOf(context),
  font: AccessibilityScope.of(context).activeFont,
),
```

Note the new parameters: 1.x took `colorSettings` and `effectsEnabled`;
2.0 takes the whole `settings`, the optional `font` and
`forceHighContrast`.

### Cupertino

New in 2.0. There was no Cupertino support in 1.x; an app that used the
Material package for a Cupertino UI can now drop it:

```dart
void main() async {
  WidgetsFlutterBinding.ensureInitialized();
  final repository = AccessibilitySettingsRepository(
    service: SharedPreferencesAccessibilityStorageService(),
  );
  await repository.load();
  runApp(
    AccessibilityScope(
      viewModel: AccessibilitySettingsViewModel(
        repository: repository,
        accessibleFonts: const [AndikaFont.font],
      ),
      child: const MyApp(),
    ),
  );
}

class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) => AccessibleCupertinoThemeBuilder(
    theme: const CupertinoThemeData(primaryColor: CupertinoColors.systemIndigo),
    builder: (context, theme) => CupertinoApp(
      theme: theme,
      localizationsDelegates: const [
        ...GlobalCupertinoLocalizations.delegates,
        AccessibilityLocalizations.delegate,
      ],
      supportedLocales: AccessibilityLocalizations.supportedLocales,
      onGenerateRoute: (settings) => AccessibleCupertinoPageRoute<void>(
        settings: settings,
        builder: (_) => const CupertinoPageScaffold(
          child: CupertinoAccessibilitySettingsPanel(),
        ),
      ),
    ),
  );
}
```

`AccessibleCupertinoThemeBuilder` yields a single `CupertinoThemeData`,
not four themes: `CupertinoApp` has no high-contrast slots, so the builder
watches the OS contrast signal and composes the high-contrast profile
itself. Use `AccessibleCupertinoPageRoute` (or `AccessibleCupertinoPage`
with a declarative `Navigator`) in place of `CupertinoPageRoute` and
`CupertinoPage`: they skip the transition when effects are off, keeping the
edge-swipe back gesture.

### A custom UI

Before (1.x), a hand-made settings screen wrote to two inherited widgets,
one for the state and one for storage:

```dart
AccessibilitySettingsInherited.of(context).updateScaleFactorSetting(1.5);
SharedPreferencesInherited.of(context).storeTextScaleFactorSetting(
  newSetting: 1.5,
);
```

After (2.0), there is one command and persistence is the repository's job:

```dart
AccessibilityScope.of(context).setTextScaleFactor(1.5);
```

State is read through the scope, which rebuilds its dependents:

```dart
final settings = AccessibilityScope.settingsOf(context);
final scale = settings.textSettings.textScaleFactor;
```

`AccessibilitySettingsBuilder` is the builder form of the same read, and
`EffectsBuilder` reports whether effects are enabled, resolving
`EffectsMode.system` against the OS reduce-motion signal:

```dart
EffectsBuilder(
  builder: (context, {required effectsEnabled, child}) =>
      effectsEnabled ? const _AnimatedHeader() : const _StaticHeader(),
)
```

Note the signature: `effectsEnabled` is a named parameter, where the 1.x
`EffectsSettingListenableBuilder` passed it positionally.

A custom UI applies the text settings once, on its root
`DefaultTextStyle`, with `AccessibleTextStyle.applyTextSettings`, and
resolves its colours with `AccessibleColor.withColorProfile`. See
[`examples/custom_ui`](../../examples/custom_ui) for a complete app.

## The settings panel

The 1.x `AccessibilitySettings` widget becomes
`AccessibilitySettingsPanel` (Material) or
`CupertinoAccessibilitySettingsPanel` (Cupertino). The record that 1.x
called `AccessibilitySettingsCollection` is now the class
`AccessibilitySettings`, which is why the widget had to be renamed.

```dart
// 1.x
const Scaffold(body: AccessibilitySettings());

// 2.0, Material
const Scaffold(body: AccessibilitySettingsPanel());

// 2.0, Cupertino
const CupertinoPageScaffold(child: CupertinoAccessibilitySettingsPanel());
```

The `style` parameter is unchanged: `AccessibilitySettingsStyle.standard`
(the default) or `.cards`, in both packages.

`AccessibilitySettingsConfiguration.all` and the
`withOnRestoreSettingsCallback` helper are gone. Use the default
constructor, which already shows everything, and pass the callback as the
`onRestoreSettings` parameter:

```dart
// 1.x
AccessibilitySettings(
  configuration: AccessibilitySettingsConfiguration.all
      .withOnRestoreSettingsCallback(() => context.go('/')),
)

// 2.0
AccessibilitySettingsPanel(
  configuration: AccessibilitySettingsConfiguration(
    onRestoreSettings: () => context.go('/'),
  ),
)
```

The same `AccessibilitySettingsConfiguration` configures both panels: the
`show...` flags, the colour candidates (`textColorCandidates`,
`backgroundColorCandidates`) and `onRestoreSettings`. Left unset, both
panels offer the same 19 Material primary swatches with their ten shades,
as 1.x did — the Material panel through `material_ui`'s `Colors`, the
Cupertino panel through `kDefaultColorCandidates`, the copy of the same
swatches that `flutter_accessibility` exports on `painting` alone.

## Stored settings

`accessibility_shared_preferences` reads the 1.x keys as they are
(`isDarkMode`, `textAccessibilitySettingScaleFactor`, `colorProfileSetting`
and the rest), so an upgraded install finds the settings its user chose.
Nothing has to be migrated by hand.

Two details:

- **Effects.** 1.x stored a boolean under the key `hasNoEffects`. 2.0
  stores a string under `effectsMode`. When `effectsMode` is absent and the
  boolean is present, `true` becomes `EffectsMode.system` — the 1.x default
  and the value every 1.x restore wrote, so an upgraded install follows the
  OS reduce-motion signal like a fresh one — and `false` becomes
  `EffectsMode.disabled`. When both are absent the value is
  `EffectsMode.system`.
- **The backend.** Apps that used `SharedPreferencesServiceLegacy` must
  construct `SharedPreferencesAccessibilityStorageService.legacy()`. On
  Android the legacy `SharedPreferences` API and
  `SharedPreferencesWithCache` store their values in different places, so
  the wrong constructor reads an empty store and the user sees the
  defaults.

The 1.x keys `themeProfileSetting` and `isFirstTimeOpened` are ignored on
read and removed by `clear()`. Sentinel values are translated on read: a
negative spacing or height becomes `null`, a `0` colour becomes `null`, an
empty family becomes `null`.

## Removed

These have no replacement:

- `AccessibleMaterialApp` and `AccessibleMaterialApp.router` — use your own
  `MaterialApp` inside `AccessibleThemeBuilder`.
- `AppThemes` — pass `ThemeData` to the builder.
- `ColorProfile.icon` — the icon maps live in the panels, so the core stays
  free of UI.
- `BuildContextControls` — the extension methods on `BuildContext`; use
  `AccessibilityScope.of(context)` and its commands.
- The exported colour constants — left unset, both panels offer the same
  19 Material primary swatches as 1.x did (the Material panel through
  `material_ui`'s `Colors`, the Cupertino panel through
  `kDefaultColorCandidates`), and a configuration can override them.
- `SettingsGroup` — the panels compose their own groups; the
  `show...Group` flags of `AccessibilitySettingsConfiguration` control
  which appear.
- `LocalStorageKeys` and `LocalStorageDefaultValues` — the keys are private
  to the storage adapter, and the defaults are on the models
  (`AccessibilitySettings.defaults`).
- `context.l10na` — use `AccessibilityLocalizations.of(context)`, whose
  getters are lowerCamelCase (`readMore`, not `read_more`).
